# This repo

What is particular to this repo. Every line below is a fact of this repo; a line left blank is a gap an agent will trip on.

## Commands

- **Unit suite.** `.venv/bin/python -m pytest -q -n auto`, run from the repo root (tests in `tests/`): `pytest-xdist` runs it across the processors the machine has, one worker each. Under `checks.py` it is also given `--testmon-noselect`, or `--testmon` in a picked run (Picked run, below). Under `checks.py` its output goes to `.checks/unit.txt`. It took 0.1 to 0.2 minutes (8 to 12 seconds, five runs on the owner's 10-processor Mac) when measured on 2026-11-18 (ticket 02 of `kit-phase-3`), down from 0.6 on one processor once its test server stopped at once (ticket 01), and 1.3 before that. A unit test must not depend on running alone or in a given order: another worker runs other tests at the same moment, in another temporary folder with a longer path, and starts and stops programs of its own.
- **Walk suite.** `.venv/bin/python walks/run_walks.py` (four workers, then each failure alone; output under `.scratch/<feature>/walks/walks-run.txt`). One walk alone: `.venv/bin/python -m pytest walks/test_needs_review_walk.py -q`. Under `checks.py` the check is named `walks`.
- **Outline a module.** `grep -n '^def \|^class ' <file>.py`
- **Every check.** `python3 checks.py` runs five checks, cheapest first, stopping at the first red: `lint` (Ruff reads the code without running it: unused imports and variables, names that do not exist, `# noqa` markers that silence nothing), `patterns` (no file matches a forbidden pattern), `escapes` (the defect log reads, and each new line names its check), `unit` and `walks`; the list is at the top of `checks.py`. A full run took 3.7 minutes when measured (2026-11-18, ticket 07 of `kit-phase-1`: unit 1.1, walks 2.6); `python3 checks.py --quick` is the quick run (below). Each check is stopped and called red at its time limit: `lint`, `patterns` and `escapes` 1 minute, `unit` 3, `walks` 8, so a whole run ends within 14 minutes. An agent's command tool waits at most ten minutes for a command, so run a whole run in the background and wait for it to end; a single check (`python3 checks.py unit`) fits in the foreground. The limits are this product's own, set at about three times a normal run (the unit suite takes about 1.1 minutes, the walks about 2.6); a product whose suites grow raises them on purpose, in `CHECKS` and in the test that pins them (`tests/test_checks.py`). Each check's output is a file under `.checks/` (git-ignored), and each run appends one line to `.checks/runs.jsonl`.
- **Quick run.** `python3 checks.py --quick` runs the same five checks with the walks at 1440 x 900 only: it leaves out every walk's 1024 x 768 run (the acceptance walk keeps its Chromium and WebKit runs at 1440 x 900, and the walk-guard tests still run). It took 2.6 minutes when measured against 3.7 for a full run (same day: unit 1.2, walks 1.4), so it saves about a minute, all in the walks. It combines with naming checks (`python3 checks.py --quick walks`). A quick run is right after a ticket and after a fix. Three runs are always full: the one before the testers and reviewers start, the one after the fixes, and the hand-over run; so is any run after a change to a file in the map's `shared` list (Walks, below), and the check on GitHub (CI, below). A quick run's line in `.checks/runs.jsonl` carries `"quick": true` (a full run's, `false`), and the hand-over page never counts a quick run as the last full run.
- **Picked run.** `python3 checks.py --pick` runs the same five checks, with the `walks` check given only the walk files a change can reach: the files that differ from the base (the commit of the last green run of every check on a clean folder, else where the branch left `main`) are placed on the map of the pages (Walks, below) by `picker.py`, and a file in `shared`, a file the map places nowhere, a missing map or a base it cannot tell runs every walk; otherwise each touched area's walk files, the changed walk files and `always`. The `unit` check is given only the unit tests that ran the code that changed (`pytest-testmon`, pinned in `requirements-dev.txt`, which records in `.testmondata`, git-ignored, which test ran which code), but only when every changed file outside `.scratch/` is a Python file: the record sees nothing else, so a changed script, page, data file or document, or a base it cannot tell, runs the whole unit suite; without a record it runs everything. A run that is not picked runs every unit test and refreshes the record (`--testmon-noselect`). `lint`, `patterns` and `escapes` run whole. It combines with `--quick` and with naming checks (`python3 checks.py --quick --pick walks`). It prints one line for each picked check, how many it ran out of how many and why (`walks     picked 2 of 42 walk files: Summary, because ... changed; and the walks that always run`; `unit      picked 12 of 767 unit tests: the tests that ran the changed Python, ...`), and its line in `.checks/runs.jsonl` carries `"picked": true`, the base in words (`base`) and, per picked check, `picks` (`ran`, `of`, `why`); every other run's line carries `"picked": false`. A picked run is right after a ticket and after a fix. The same three runs as for a quick run (before the testers and reviewers start, after the fixes, the hand-over run) and the check on GitHub are always whole, and a picked run is never a full run, whatever it happened to run.
- **The linter.** The `lint` check is Ruff, pinned to one exact version (`ruff==0.17.5` in `requirements-dev.txt`) so that a new release of Ruff cannot turn a build red on its own: the same commit gets the same result next month. Its rules are written out in `ruff.toml` (`E4`, `E7`, `E9`, `F`, `RUF100`), with nothing left to Ruff's defaults, which have changed between releases. A rule group is added at a retro, one at a time and on purpose, never to make a build pass; code is fixed to pass the rules, not silenced. The check writes no cache.
- **The proof that the checks can fail.** `python3 prove.py` makes each deliberate break in `docs/agents/local/breaks.json` in a fresh copy of the repo (the working folder is never touched) and runs the test or check the entry names, once unbroken (it must be green) and once broken (it must be red); it ends 0 only when every break was caught, prints one line per break and appends one line to `.checks/proof.jsonl`. Its ten breaks took 0.43 minutes when measured (2026-11-18, ticket 07 of `kit-phase-2`): each walk break runs one walk, not the whole `walks` check, because each run has a two-minute limit. It is run by hand, after a change to a check and before a retro, and is not part of `python3 checks.py`. Every check in `CHECKS` must have at least one break in the list (a break whose test is under `tests/` counts for `unit`, under `walks/` for `walks`); `tests/test_prove.py` holds that, so a new check needs a break.

## Walks

- **Tooling.** Playwright for Python with Chromium (`requirements-dev.txt`; once: `.venv/bin/python -m playwright install chromium`), run by pytest in `walks/`, outside the unit folder (`pytest.ini` points the unit suite at `tests/`). The pages are exercised only by the walks; the unit suite tests the API and the Python modules, with no browser.
- **Helpers.** `walks/helper.py` (the app in a subprocess on a free port over a fresh temporary database, the stand-in registry, the guards: console error, page error, failed or foreign request, sideways scroll; seeded data `seed_queue`) and `walks/conftest.py` (fixtures `make_app`, `make_walk`, `registry`, `viewport`; a walk whose guards tripped is reported FAILED). `walks/standin_registry.py` is the stand-in registry; `walks/serve.py` starts the app against it. A walk is `walk = make_walk(make_app(seed=...))`, then acts through `walk.page` by role and name.
- **Walk output.** `.scratch/<feature>/walks/` (git-ignored): `<walk>-NN-<step>.png`, a `-final` shot of every failed walk, and `walks-run.txt`.
- **Recording a walk.** `WALK_RECORD=<folder>` records each walk's page as `<folder>/<walk>.webm`, slowed so a person can follow it (`WALK_SLOW_MO` milliseconds a step, default 350). `python3 handover.py <feature>` uses it to record, for the hand-over page, the walks a build added or changed (a test function in `walks/test_*.py` with a changed line of its own) that its `hand-over.json` lists under `walk_through`, each once at 1440 x 900; a build that changed none gets the acceptance walk. Unset, nothing is recorded and nothing is slowed.
- **The map of the pages.** `docs/agents/local/walk-map.json` says which files every page shares (`shared`: a change to one runs the whole walk suite, in a full run, never `--quick`), which walk files always run (`always`), each area's source files and the walk files that cover it (`areas`), and which files reach no walk (`none`). A new source file goes in the area whose page it draws or serves, or in `shared` when in doubt; a new walk file goes in the `walks` of every area it opens. `tests/test_walk_map.py` reads it with `walk_map.py` and is red, naming the file, while any file or walk file is placed nowhere, a pattern matches nothing, a listed walk file is gone or an area has no walk.
- **Viewports.** 1440 x 900 and 1024 x 768 (every walk runs at both in a full run, at 1440 x 900 only in a quick run); the acceptance walk (`walks/test_acceptance_walk.py`) runs at both in Chromium and at 1440 x 900 in Playwright's WebKit (`.venv/bin/playwright install webkit` once; it is part of the walks check). The browser runs in Asia/Tokyo and the server in America/New_York, so a time shifted into the browser's zone shows.
- **Agents running browsers at once.** 3 (a suite run uses four workers; the runner re-runs a failure alone, so load-only flakes show as such: each run appends the walks that were red under load and green alone to `.scratch/<feature>/walks/flaky.jsonl`, and the hand-over page lists each one for the owner and says when that record is missing for the build's last run of the walks).
- **Not checkable by a walk here.** Wording and legibility, Safari, real hardware, the live registry (`walks/fidelity_check.py` is by hand).

## Running a walk

Write `walk = make_walk(make_app(seed=helper.seed_queue))`, `walk.page.goto(app.url)`, act by role and name, assert on what is drawn, `walk.shot("step")`. The stand-in registry's switches are `registry.set("revise")` and so on (its control endpoint, never the app). A new guard or helper change runs `walks/test_walk_guards.py`, which runs deliberately broken pages in `walks/broken/`. A walk that proves an error response declares it first with `walk.expect(status, path)`; the guards then treat that response as expected, and fail the walk if it never comes.

A script outside `walks/` (a walker's or reviewer's, under `.scratch/<feature>/findings/scripts/`) runs from the repo root with `WALK_FEATURE=<feature> .venv/bin/python -m pytest -p walks.conftest <script> -q`; a unit one with `-p tests.conftest`. The `-p` loads the fixtures and the hook that fails a walk whose guards tripped; do not copy or import the fixtures by name instead, because that leaves the hook out.

## What checks the stand-ins

- **The registry stand-in's filters.** Nothing narrows by phase, status or date, so `walks/test_find_trials_walk.py` asserts the parameters in the stand-in's recorded requests.
- **The patched `time.sleep`.** The unit tests skip the pause between registry calls; `walks/test_check_walk.py` runs a check against the stand-in's `slow` switch with the real sleep.

## CI

- **Workflows.** One: `.github/workflows/checks.yml`, with one job named `checks` (the status check the owner requires on `main`). It runs when a pull request is opened, pushed to, reopened or marked ready for review (drafts included, no path filter), and by hand; never on a push. It makes the repo's `.venv` with Python 3.13, installs both requirements files and Playwright's Chromium and WebKit (WebKit for the acceptance walk, part of the `walks` check), and runs the full `python3 checks.py` with no check named (never `--quick`, so both window sizes). Its limit is 20 minutes; a newer run on the same branch cancels the older one, and on red the files under `.checks/` are uploaded with the run. Before the checks, a notice in the run's summary lists the files the pull request changes that judge it (`.github/workflows/`, `checks.py`, `.claude/settings.json`, `pytest.ini`, `ruff.toml`: the linter's rules) and how many tests it removes (`.github/workflows/judge_notice.py`); it never fails the run. A pull request runs its own branch's copy of the workflow, merged with `main`, so the notice is for the owner to read, not a guard. `tests/test_workflow.py` holds what the file says, and that this line names every workflow file there is; nothing here runs it on GitHub. The old Pages publish workflow is retired.
- **Merging.** Merging a pull request is the owner's: `.claude/settings.json` refuses the command `gh pr merge` to the building agent, and that refusal stops that command only, not every other way a merge could be made.
- **Local hooks.** None. `python3 checks.py` is run by hand and by `/implement-spec` after every ticket.
