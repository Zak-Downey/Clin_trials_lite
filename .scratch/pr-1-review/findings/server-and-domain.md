## Blocking

1. **The Summary's "Latest:" line can name an older check's fields, not the newest check's.** `briefing.summarise` sorts each trial's moves so that high-signal fields come first, across all checks (`briefing.py:202`). `_latest` then treats `moves[0]["detected"]` as the newest check (`webapp/api_summary.py:52`). Take a trial whose newest check moved only a low-signal field (brief title, on 5 Nov) and whose older check moved a high-signal one (completion date, on 3 Nov). Its summary line reads "Latest: completion date updated." That is the older check, and the newest change goes unnamed. The analyst is the one exposed: this is the line they brief from (story 87, design 10/4). The ticket's own test means to pin this exact rule ("names the newest check's fields only, not the older check's title", `tests/test_api_summary.py:112`). It cannot fail on it, because its fixture moves only enrolment and brief title, and neither is high-signal. Fix: take the newest stamp as `max(m["detected"] for m in entry["moves"])`, and add a fixture with a high-signal field in the older check. | `webapp/api_summary.py:50-58`, `briefing.py:202` | **Reproduced** (`/tmp/rv/latest.py`): the moves came back in the order `[('completionDate', '…11-03…'), ('briefTitle', '…11-05…')]` and `_latest` returned `Latest: completion date updated.` | blocking

## Design

2. **The saved-search cap applies to the search's first 100 results, not to 100 new matches per run. Matches past the 100th are never offered.** `find_new` asks the registry for 101 results and looks only at the first 100 (`monitor.py:673`). It then skips the ones that are already members or already offered. Once the analyst has added or dismissed those 100, every later run offers nothing and reports "Nothing new matched. The search matched more than 100; narrow it." The spec says "New matches are capped at 100 per saved-search run". Read naturally, that offers up to 100 *new* matches each run, so a later run would reach the 101st. The implementation narrows this. It is not silent (the cap note shows), but "Nothing new matched" is untrue when 50 unseen matches exist. Decide which reading is meant. If the current one stays, the result should not say "Nothing new matched" while capped. | `monitor.py:648-715` | **Reproduced** (`/tmp/rv/cap.py`, 150 matching studies): run 1 offered 100; after those were dismissed, run 2 offered 0 with "Nothing new matched. The search matched more than 100; narrow it." | design

## Sweep

4. **Two handlers choose the error `kind` by matching message text.** `api_search.py:30` and `api_saved_search.py:57` map a `MonitorError` to `nothing_asked` when `"at least one" in str(err)`, and to `bad_dates` otherwise. `MonitorError` now carries a `kind` (added on this branch), but `_refuse_unanswerable` raises both refusals with the default kind `"error"`. Rewording `NOTHING_ASKED` would silently turn every empty-form refusal into `bad_dates`. The page would then show the error beside the wrong field. The spec rules this out: "as error types or codes the API maps to messages, not message text". Give the two refusals their own kinds in `monitor._refuse_unanswerable`. | `webapp/api_search.py:30`, `webapp/api_saved_search.py:57`, `monitor.py:449-467` | read | sweep

5. **The stand-ins row for the stub fetcher and finder is stale, and the real search client is not unit-tested.** `docs/agents/local/repo.md:33` still says "None yet: no endpoint calls the registry". Lookup, details, add, search and checks all call it now, through `make_fetcher`/`make_finder` and a third stub, `find_page` in `tests/test_api_search.py:24`. That stub has no row. It is also the stub that does the paging, so `ctgov.find_page`'s own logic (`pageSize = page*10`, then a slice) is not exercised by any unit test. Only the walks reach it, and only against the stand-in registry, whose search answers are not compared with the live service (the row says so). Update the row, add `find_page` to it, and add one unit test of `ctgov.find_page` over a stubbed `_get`. | `docs/agents/local/repo.md:33`, `ctgov.py:253-281`, `tests/test_api_search.py:24` | read: grepped `find_page` in `tests/` and `walks/` | sweep

6. **CSV formula injection (judging the logged observation): sweep, not blocking.** `as_csv` writes cells as they are (`briefing.py:318` onward). Titles and values come from sponsors through the registry, and the watchlist name comes from the analyst. A cell beginning `=`, `+`, `-` or `@` is evaluated when the file is opened in Excel or Numbers, which is how a briefing CSV gets used. The risk is real but bounded. The registry is moderated, the file stays on the analyst's machine, and modern Excel warns before running external-link or DDE formulas. Accidental corruption is the likelier harm: a value beginning `-` or `+` shown as `#NAME?`. Empty values are written as an em dash (`display.EMPTY`), not a hyphen, so they are safe. The "exact values" clause can be kept by prefixing `'` only to cells whose first character is one of `= + - @ \t \r`, and saying so in a CSV note. Fix it in the follow-up spec, as Further Notes already plans. | `briefing.py:306-338` | read | sweep

7. **A check reads its trial list once at the start, so a trial removed during the run is still checked.** `_start` fixes `steps` from `list_trials` when the run begins (`webapp/api_checks.py:79-90`). `_work` then releases the lock on every fetch, so the analyst can remove a trial, or delete the watchlist, while the run is going. A removed trial that is in no other list is now unmonitored, yet it is still fetched and gets `mark_checked` and new changes. The spec says it "is skipped by every check". Deleting the watchlist mid-run checks every trial it held, all of them now unmonitored. Re-read membership under the lock before each step (`storage.is_member(conn, list_id, nct)`). | `webapp/api_checks.py:58-82` | inferred from code (the lock release is what the readable-while-checking test proves) | sweep

8. **A list deleted while `add_trials` is fetching gets orphan membership rows.** `add_trials` reads the target list, then releases the lock to fetch (`webapp/api_membership.py:51`). If the list is deleted in that window, `adopt_many`, then `add`, then `add_member`, still insert `list_members` rows for the deleted id (`api_membership.py:59`). `list_trials(conn, None)` treats an orphan row as monitored, while `lists_holding` says no list holds the trial. ## Nit

9. **The run's `finally` block has no guard of its own.** If `finish_run` or `last_check_run` raises (a sqlite error such as a full disk), `run.running` stays `True`. Every later Check for updates on that watchlist then gets a 409 until the server restarts, which is the outcome the `except` comment exists to prevent. Set `running = False` in an inner `finally`. | `webapp/api_checks.py:76-80` | read | nit

10. **A crash mid-run is not retryable.** An exception other than `MonitorError` (in the profile, the diff or sqlite) ends the run with `crashed` set. The trial it hit is never added to `results`, so it is not counted as failed, and `failed_in_last_run` leaves it and every trial after it out of Retry failed. The state does read "incomplete", so it is not an all-clear. | `webapp/api_checks.py:62-75`, `monitor.py:969-975` | read | nit

11. **Undoing a removal after the trial was added to another list leaves a lone "resumed" in History.** `restore` deletes the `stopped` event named in the token (`monitor.py:327`). If, between the removal and the undo, a different list took the trial back, the `resumed` event written then stays, and the timeline shows "resumed" with no "stopped" before it. `forget_monitoring_event` also deletes by id without checking that the event belongs to that trial. | `monitor.py:324-328`, `storage.py:350-353` | inferred | nit

12. **A malformed request body gets a 500, not a 400.** A JSON body that is not an object (for example `[]`) reaches `(body or {}).get(...)` and raises `AttributeError`. A non-numeric `Content-Length` raises `ValueError` in `_body`. Both surface as `server_error` with Python's exception text. Only the page sends requests, so the impact is small. | `webapp/server.py:75-83` | read | nit

13. **After every watchlist is deleted, a restart creates "My watchlist" again.** `_house_every_trial` runs on any connect that finds no lists. It skips trials with a `stopped` event, so no trial is re-homed, but an analyst who deleted every watchlist finds a new empty "My watchlist" on the next start. Its docstring also still says "a trial that loses its last list … is deliberately dropped", which retention has made false. | `storage.py:171-198` | read | nit
