## Comments

**What was read too early.** The walk's first read, the review bar's sentence "Review covers all 5 changes shown above.". The trial page drew that sentence (and the "5 unreviewed changes" heading and the tab's count) only at the very end of drawing the page, after a second request, the watchlist's queue (`/api/watchlists/<id>/needs-review`, used only to find the next trial), had answered. The bar itself, its "Also clears these changes in: Elsewhere." line and both buttons were already on the screen, so the walk's wait for the "Mark reviewed" button let it read a bar whose first line was still blank. Under load that queue answers late, and the walk went red; alone it answers at once, and the walk went green. The wobble records (`.scratch/kit-phase-2/walks/flaky.jsonl`, `.scratch/kit-phase-4/walks/flaky.jsonl`) do not keep the failing line, so I assume from the slowed walk below that the wobble failed on this read; nothing records it.

**Shown red first.** A new walk, `test_walk_the_action_bar_states_its_scope_while_the_watchlist_s_queue_is_still_unanswered` in `walks/test_trial_page_walk.py`, holds the queue's answer in the browser (a Playwright route), opens the trial, waits as the old walk does for the "Mark reviewed" button, then makes every one of the old walk's reads (moved, unchanged, into one function both walks call). Before the fix it was red at both window sizes on the first read, the bar's text being `'\n\nAlso clears these changes in: Elsewhere.\nNext trial\nMark reviewed'`; after the fix it is green. It then lets the queue answer and checks that "Next trial" still opens the next trial.

**The page's fault, not the walk's.** A person saw a bar with buttons and a blank first line for as long as the queue took, and could act in that moment. The page now draws the sentence, the heading and the count before it asks for the queue (`webapp/static/views/trial.js`), so the "Mark reviewed" button never appears without them. The old walk's wait is now enough: it waits for the "Mark reviewed" button, which the page now draws in the same step as everything the walk reads. I wrote that the scroll reads were not racing; that was wrong, as the review found (`review-trial-page-01`). The page jumped back to the top when the watchlist's queue answered, because the page's move to the top waited for that answer, so a queue answering between the walk's scroll to the bottom and its read of the last change turned the walk red. The page now moves to the top as soon as it is drawn and no longer waits for the queue to do so; the walk `test_walk_the_last_change_stays_clear_of_the_bar_when_the_queue_answers_after_the_scroll` holds that race. A scroll by script moves the page at once, and nothing that changes the page's height is drawn after the button any more. No assertion was loosened, and no retry or pause was added. Defect log: E-043.

**Seen, then fixed.** In the same moment, before the queue answers, "Next trial" was enabled but did nothing when clicked, because its action is attached only once the queue is known. The early read found it as `early-read-whole-01`; it was fixed in e2148f8: the button is now drawn disabled until the queue answers.

**The last box.** I ran the whole browser suite three times in a row on commit d8782d5, at both window sizes (`WALK_FEATURE=kit-phase-5 .venv/bin/python walks/run_walks.py`): each run passed 415 of 415 walks and recorded no wobbling test (`.scratch/kit-phase-5/walks/flaky.jsonl`, three lines with `"flaky": []`, plus a fourth from the full check run). `python3 checks.py` (full, both window sizes) ended green on d8782d5 in 2.1 minutes. Three earlier runs before that commit also passed 415 of 415 with no wobble.
